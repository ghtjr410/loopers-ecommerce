## Test A. 대기열 없이 직접 주문 — 서버 한계 증명

### 목적
대기열 보호 없이 500 VU가 직접 `POST /orders`를 때리면 SLO가 위반됨을 증명한다.

### 설정
| 항목 | 값 |
|------|-----|
| VU | 0 → 200 → 500 (ramping) |
| 지속 시간 | ~130초 |
| 서버 모드 | NORMAL (대기열 비활성) |
| Rate Limit | 비활성 (`order-limit-per-minute: 99999`) |
| 대상 상품 | NORMAL 상품 ID 4~10 (재고 99,999) |

### 실행
```bash
k6 run k6/queue/a-no-queue.js
```

### 결과

| 지표 | 값 | SLO | 판정 |
|------|-----|-----|------|
| **p50 응답시간** | 452ms | - | |
| **p90 응답시간** | 992ms | - | |
| **p95 응답시간** | 1,250ms | - | |
| **p99 응답시간** | 2,050ms | ≤ 500ms | ❌ SLO 4.1배 초과 |
| **최대 응답시간** | 2,990ms | - | |
| **성공률** | 100% | ≥ 99.9% | ✅ |
| **SLO 위반 건수** | 37,764건 (40.8%) | - | |
| **총 요청** | 92,615건 | - | |
| **실측 TPS (평균)** | 712 TPS | 안전 TPS 424 | 1.68배 초과 |

### 관찰 사항

> - 500 VU sustained 구간에서 p50이 이미 452ms로 SLO 경계에 근접
> - p99 2,050ms → SLO(500ms)의 4.1배 초과
> - 전체 요청의 40.8%가 500ms를 초과 — 유저 10명 중 4명이 느린 응답 체감
> - 5xx 에러는 0건이지만, 응답시간 기준으로 서비스 품질 심각하게 저하
> - TPS 712로 안전 TPS(424)를 68% 초과 — DB 쓰기 부하가 Tomcat/Hikari를 포화시킴

## Test C. 고정 Rate 입장 — TPS 분산 증명

### 목적
10초마다 125명 입장하는 고정 rate가 Thundering Herd 없이 주문 TPS를 평탄하게 분산함을 보인다.

### 설정
| 항목 | 값 |
|------|-----|
| VU | 500 |
| 입장 배치 | 125명 / 10초 |
| 구경 시간 | 2~15초 (랜덤) |
| 총 소요 시간 | 95초 |

### 실행
```bash
k6 run k6/queue/c-tps-distribution.js 2>&1 | tee k6/result-c.log
grep "\[ORDER\]" k6/result-c.log | sed 's/.*bucket=\([^ ]*\).*/\1/' | sort -t'-' -k1 -n | uniq -c
```

### 결과

| 구간 (초) | 주문 건수 | 추정 TPS |
|-----------|----------|----------|
| 20-30s | 85 | 8.5 |
| 30-40s | 40 | 4.0 |
| 40-50s | 94 | 9.4 |
| 50-60s | 31 | 3.1 |
| 60-70s | 87 | 8.7 |
| 70-80s | 38 | 3.8 |
| 80-90s | 71 | 7.1 |
| 90-100s | 54 | 5.4 |

**피크 TPS**: 9.4 TPS (구간: 40-50s)
**평균 TPS**: 6.3 TPS
**피크/평균 비율**: 1.5배

### 분석

> - 피크 구간(40-50s)에서 9.4 TPS → 안전 TPS 424의 **2.2%만 사용**
> - 피크/평균 비율 1.5배 — Thundering Herd 없이 고르게 분산
> - 10초 구간별 주문이 31~94건 범위로 분포 → 스파이크 없는 평탄한 패턴
> - 구경 시간(2~15초 랜덤)이 배치 내 주문 시점을 자연 분산시킴
> - 시나리오 역산 최대 피크: 125 × 0.6 × 0.3 / 10 = 2.25 TPS (1/10 축소) → 실측 피크 9.4 TPS는 구경 시간 분산 효과 포함

## Test D. CAS 동시 주문 — 단건 보장 증명

### 목적
같은 userId로 10건의 동시 주문 요청 시 CAS가 정확히 1건만 성공함을 증명한다.

### 설정
| 항목 | 값 |
|------|-----|
| VU | 10 (shared-iterations) |
| 대상 userId | 999 |
| 동시 요청 | 10건 |

### 실행
```bash
k6 run k6/queue/d-cas-concurrency.js
```

### 결과

| 응답 | 건수 | 기대값 | 판정 |
|------|------|--------|------|
| **200 OK (주문 성공)** | 1건 | 1건 | ✅ |
| **409 Conflict (CAS 실패)** | 9건 | 9건 | ✅ |
| **기타 (401/403/500)** | 0건 | 0건 | ✅ |

### VU별 상세

| VU | Status | Duration |
|----|--------|----------|
| 1 | 409 | 205ms |
| 2 | 409 | 207ms |
| 3 | 409 | 202ms |
| 4 | 409 | 204ms |
| 5 | 409 | 207ms |
| 6 | **200** | **194ms** |
| 7 | 409 | 202ms |
| 8 | 409 | 204ms |
| 9 | 409 | 205ms |
| 10 | 409 | 202ms |

### 분석

> - 200 OK: 정확히 1건 (VU 6) → CAS(ACTIVE→CONSUMED) Lua 스크립트가 원자적으로 1건만 성공
> - 409 Conflict: 9건 → 나머지 모두 상태 불일치(CONSUMED)로 즉시 거부
> - 기타: 0건 → SessionFilter 통과 후 CAS까지 세션 만료 없이 정상 경합
> - 10건 모두 194~207ms 범위 → 거의 동시에 도달하여 경합이 발생했음을 확인
> - **결론**: Redis Lua CAS로 분산 환경에서 Lock 없이 1인 1주문 원자적 보장

## Test G. 전원 입장 시간 실측 — 역산값 검증

### 목적
500명 대기열 진입 후 전원 입장까지의 시간을 측정하여 시나리오 역산값과 대조한다.

### 역산 기대값

```
500명 ÷ 125명/배치 = 4배치 × 10초 = 40초
+ 진입 분산 (IP rate limit + random sleep) ≈ +10초
→ 기대값: ~50초
```

### 설정
| 항목 | 값 |
|------|-----|
| VU | 500 |
| 입장 배치 | 125명 / 10초 |

### 실행
```bash
k6 run k6/queue/g-drain-time.js 2>&1 | tee k6/result-g.log
grep "\[ADMITTED\]" k6/result-g.log | tail -1
```

### 결과

| 지표 | 실측값 | 역산 기대값 | 오차 |
|------|--------|-----------|------|
| **전원 입장 시간** | 65초 | ~50초 | 30% |
| **개인 대기 p50** | 30초 | - | |
| **개인 대기 p90** | 56초 | - | |
| **개인 대기 p95** | 56초 | - | |
| **입장 성공** | 500명 / 500명 | 500명 | ✅ |
| **입장 실패** | 0명 | 0명 | ✅ |

### 분석

> - 전원 입장 65초 → 역산 50초 대비 오차 30%
>   - 오차 원인: 진입 분산(random sleep 0~10초)으로 마지막 VU가 10초 지점에 진입
>   - 실제 대기열 소진 시간: 65 - 10(진입 분산) = 55초 ≈ 역산 40초 + 스케줄러 간격 오차
> - 개인 대기 p50 30초 → 중앙 유저는 30초 대기 후 입장
> - 개인 대기 p90 56초 → 마지막 배치 유저도 1분 이내 입장
> - 500명 전원 입장 성공, 유실 0건 → ZRANGE → SET → ZREM 순서의 유실 방지 동작 확인

> **시나리오 검증**: 역산 공식(M=125, N=10초)이 실측과 합리적 범위 내 일치.
> 진입 분산을 보정하면 대기열 소진 시간은 역산값에 근접하며, 가정 기반 용량 설계의 신뢰성을 확인함.
